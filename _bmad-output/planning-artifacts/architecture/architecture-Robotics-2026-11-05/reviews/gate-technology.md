# Technology and reality-check gate

Date: 2026-11-05. Scope: read-only review of ARCHITECTURE-SPINE.md and docs/TRD.md, especially sections 2, 6, 10–14. Only this review artifact was written. Official documentation and upstream source were checked live; no implementation, installation, hardware operation or qualification was performed.

## Verdict

**PASS for documentation finalization, with the existing T1–T6 qualification gates still open. No actionable blocking technology finding.**

The named technologies expose the required building blocks. The documents distinguish those building blocks from custom safety behavior, actual compatibility and measured performance. AD-8/AD-14 expressly defer the exact package/checkpoint/GPU combination to T1/T5; absence of version pins at this stage is an authorized gate, not a failed selection. This verdict does not close T1 or establish that the selected laptop, controllers, modules or physical stopping targets work.

## Evidence and assessment

| Area | Verified reality | Assessment of proposed contract |
| --- | --- | --- |
| Next.js starter and local Node release | The official installation page documents create-next-app, customization prompts, TypeScript and Windows support. Its defaults include optional choices such as Tailwind; self-hosting documents next start and distinguishes it from static export. [Installation](https://nextjs.org/docs/app/getting-started/installation), [self-hosting](https://nextjs.org/docs/app/guides/self-hosting). | AD-4 and TRD section 2 correctly select a local production Node service and explicit starter settings. No hosting provider or static export is accidentally required. The live starter's changing defaults must be recorded at T1 rather than blindly adopted. No app manifests or lockfiles were found in the project scan; the starter is selected, not instantiated or verified. |
| FastAPI REST and WebSocket | FastAPI documents validation/OpenAPI, Uvicorn operation, ordinary HTTP endpoints and bidirectional WebSockets carrying binary, text or JSON. Dependencies can also protect WebSocket connections. [Features](https://fastapi.tiangolo.com/features/), [server operation](https://fastapi.tiangolo.com/deployment/manually/), [WebSockets](https://fastapi.tiangolo.com/advanced/websockets/). | The REST/event/video split is supported. Single backend worker and separate inference process are consistent with one hardware/state owner. Framework examples do not supply the application's safety loop, bounded queues or readiness logic; the TRD explicitly requires those. Explicit loopback binding is necessary because upstream deployment examples also show all-interface listeners; section 10 already requires it. |
| Backend webcam | OpenCV's official capture interface accepts device indices and preferred capture backends, including Windows capture APIs. [videoio source](https://raw.githubusercontent.com/opencv/opencv/4.x/modules/videoio/include/opencv2/videoio.hpp). | Backend ownership of webcam acquisition is realistic and avoids a browser-owned capture dependency. OpenCV decoding does not establish ESP32 capture freshness; TRD section 2 explicitly keeps metadata outside the decoder. Actual camera/driver readiness remains T3/T4. |
| MediaPipe landmarks | Hand Landmarker provides local Python support, multiple-hand outputs, normalized image coordinates, world coordinates and handedness; it offers video/live-stream modes. [Python setup](https://developers.google.com/edge/mediapipe/solutions/setup_python), [Hand Landmarker](https://developers.google.com/edge/mediapipe/solutions/vision/hand_landmarker). | Deriving mirrored pointing directions from landmarks is technically plausible. The document correctly does not claim canned gesture categories provide four arbitrary pointing directions. Thresholds, ambiguity, handedness/mirroring and timing need T4 qualification. Defaults are not acceptance settings: Python's documented num_hands default is one, so an implementation must configure enough hand detection to enforce the required multiple-hands stop. |
| YOLOE visual prompts | Ultralytics documents reference-image boxes and class IDs supplied through visual_prompts and refer_image, including reuse for later frames. Prompt-free checkpoints are distinguished from prompt-capable ones. [YOLOE visual prompting](https://docs.ultralytics.com/models/yoloe/). | The reference image plus ROI maps to a real model mechanism. It is not a promise of unique-instance identity or success on five chosen objects; the contract retains human confirmation and T5 benchmarking. Selection must retain a visual-prompt-capable checkpoint and explicit separate reference semantics rather than accidentally prompting the first robot frame. No checkpoint is invented by this review. |
| Local PyTorch/NVIDIA runtime | PyTorch's installer offers Windows and compute-platform selections plus verification guidance. [Local installation](https://pytorch.org/get-started/locally/). | A local GPU inference path exists, but only the eventual machine/package/driver lock can establish compatibility. T1's reproducible environment and T5's actual benchmark are honest gates. Documentation from independently moving projects is insufficient to assert an already compatible combination. |
| Pygame/SDL controller ownership | Pygame documents joystick hats/buttons, instance IDs and hotplug events; its controller API includes controller removal/remapping and common DualShock-style layouts. Regular event pumping is required. SDL documents an explicit background-event hint whose default disables background events. [Joystick](https://www.pygame.org/docs/ref/joystick.html), [controller](https://www.pygame.org/docs/ref/sdl2_controller.html), [SDL background events](https://wiki.libsdl.org/SDL2/SDL_HINT_JOYSTICK_ALLOW_BACKGROUND_EVENTS). | Backend controller reading is supported. TRD 6.1 already calls out independent pumping, browser-workspace gating and actual PS4/PS5 profile qualification, avoiding an assumption that browser focus makes the Python process foreground. The implementation must initialize/pump SDL correctly and permit backend background input where needed; device support and mappings are not yet proven. |
| SQLite and Python sqlite3 | SQLite supports foreign keys, composite relationships and cascading actions, with enforcement requiring connection configuration. Python documents its local disk database interface and transaction control. [Foreign keys](https://www.sqlite.org/foreignkeys.html), [sqlite3](https://docs.python.org/3/library/sqlite3.html). | Serialized writes, explicit transactions, per-connection foreign keys and an actual-engine inventory are realistic. The TRD correctly does not claim a SQL transaction can atomically include external file rename/deletion; its separate storage journal/reconciliation is application work. Durability settings remain T1 evidence. |
| pySerial and HC-05 path | pySerial documents Windows COM access and finite/nonblocking read configurations, including the danger of unbounded readline. [pySerial introduction](https://pyserial.readthedocs.io/en/latest/shortintro.html). | Python-side bounded serial I/O is available. Command leases, generations, sequence checks, challenges, ARM and watchdog behavior require custom backend/Uno firmware. Section 6.3 clearly describes that requirement without claiming generic serial provides it. Purchased HC-05 behavior and link coverage remain T2/T3; no manufacturer-variant qualification is inferred. |
| ESP32 acquisition freshness | CameraWebServer's current stream source emits X-Timestamp from camera_fb_t.timestamp, preserving it before JPEG conversion. The camera driver's header defines that field as boot-relative timing of the frame's first DMA buffer. [CameraWebServer source](https://raw.githubusercontent.com/espressif/arduino-esp32/master/libraries/ESP32/examples/Camera/CameraWebServer/app_httpd.cpp), [camera driver header](https://raw.githubusercontent.com/espressif/esp32-camera/master/driver/include/esp_camera.h). | The cited acquisition timestamp building block is real. It is not wall-clock synchronization, full sensor-exposure timing, an epoch/sequence protocol or a bounded age guarantee. TRD 6.2 accurately requires custom epoch/sequence metadata, round-trip uncertainty bounds and displayed-frame acknowledgments. T6 must validate those bounds, camera buffering/sensor timing and end-to-end video latency on the pinned firmware. No assumption that ordinary MJPEG arrival establishes freshness was found. |

## Open work preserved by this verdict

1. T1 must lock the actual supported Node/Python/package/SQLite/GPU environment and local assets; this review does not select package numbers from live documentation.
2. T3/T4 must demonstrate the actual webcam, PS4 and PS5 profiles and both radio links on the fixed-desk route. Library support is not equipment qualification.
3. T5 must demonstrate the required matching/false-alert counts, local offline loading and continuity behavior using the selected checkpoint and target set.
4. T6 must implement and test the custom camera/command protocols and measure physical stopping, display latency and endurance under full load. Source timestamps and logical output acknowledgments do not establish those outcomes.

The above are existing exit gates and implementation cautions, not newly imposed scope or documentation blockers. No code tests or hardware trials were run, no benchmark was inferred, and no source document was edited.
