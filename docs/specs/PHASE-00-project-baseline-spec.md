# Phase 00 — Project baseline and execution setup

## Problem Statement

The Lost and Found team has approved product and technical plans, but does not yet have an execution baseline showing who owns the work, what equipment is actually available, which assessment details are confirmed, or how each requirement will be verified. Starting implementation without that baseline risks missed requirements, unresolved safety decisions, unsupported completion claims, and missing report evidence.

The first phase is Phase 00, not Phase 01. Its purpose is to make the planned work accountable and reviewable before hardware preparation and application development begin.

## Solution

Produce one reviewable baseline package containing the source baseline, phase and gate ownership, current inventory, assessment and milestone record, acceptance/evidence index, blocker/decision register, source-control conventions, and report outline.

The package must let a team member trace every approved requirement to its implementation phase, planned verification, responsible person, and eventual evidence. It must distinguish reported information from inspected equipment and measured results. Missing information remains explicitly pending with an owner and next action; it never becomes an invented date, electrical value, approval, or test pass.

This specification defines the work to perform. Creating or publishing it does not complete Phase 00.

## User Stories

1. As an execution lead, I want an identified baseline of the approved documents, so that everyone starts from the same requirements and decisions.
2. As an implementer, I want the authority of the PRD, architecture, TRD, UX guidance, and implementation guide recorded, so that implementation convenience cannot silently change approved behavior.
3. As an execution lead, I want a named owner for Phase 00 and each of Phases 01–17, so that every deliverable has an accountable person.
4. As a gate owner, I want each of T1–T7 assigned with its required exit evidence and deadline condition, so that unresolved decisions reach the right person before dependent work starts.
5. As a team member, I want the actual phase dependencies and hardware-first execution order recorded, so that apparently parallel work does not bypass the agreed sequence.
6. As an execution lead, I want actual team availability recorded, so that milestone commitments reflect the people available to do the work.
7. As an assessment coordinator, I want the assessment date, time, report format, demonstration format, and submission instructions confirmed with the supervisor, so that delivery planning follows the real assessment.
8. As an execution lead, I want unconfirmed assessment details visibly marked pending, so that a planning target is never mistaken for a supervisor-confirmed deadline.
9. As a team member, I want milestone dates derived from confirmed instructions and availability with contingency time, so that failed trials, repairs, and reruns fit into the plan.
10. As a hardware lead, I want a current inventory of the prescribed parts and quantities, so that reported purchases can be reconciled with what is available for inspection.
11. As a laptop and input lead, I want the laptop, Windows/GPU information, built-in webcam, PS4 DualShock 4 unit, and connection capabilities recorded, so that later qualification uses identifiable equipment.
12. As an integration lead, I want existing network access and the proposed fixed-desk route through two adjacent rooms recorded, so that missing route information is resolved before coverage qualification.
13. As a hardware lead, I want unknown component variants, ratings, condition, and compatibility marked unresolved, so that a purchase record or photograph is not mistaken for electrical clearance.
14. As an evidence lead, I want one acceptance-index entry for every FR, NFR, and success metric, so that no approved requirement disappears between implementation and assessment.
15. As a verifier, I want each entry to identify its owner, planned test, relevant phases, configuration, and evidence, so that a later result can be reproduced and assessed.
16. As a supervisor, I want all acceptance results initially Pending and later evidence classified by test level, so that simulated or bench checks cannot be represented as assessed whole-system performance.
17. As an implementer, I want a blocker/decision register with gate, owner, required evidence, affected work, and next action, so that open questions block their dependent work without stopping unrelated permitted work.
18. As a reviewer, I want existing source control and the normal review workflow documented, so that contributors can submit coherent changes without inventing a new commit policy.
19. As a laptop user, I want secrets, runtime records, and private images excluded from source control, so that development artifacts do not expose operational data.
20. As a report author, I want an assessment-aligned report outline and evidence collection conventions from the start, so that the final report can use recorded results rather than reconstruct measurements.
21. As a hardware lead, I want the Phase 01 handoff to show its prerequisites and still-open T2 decisions, so that baseline completion cannot be interpreted as wiring, charging, or movement approval.
22. As an execution lead, I want a documented baseline-package review and unresolved-item list, so that the team can determine whether Phase 00 is complete without claiming later implementation has passed.

## Implementation Decisions

- **Deliver documentation and registers only.** This phase creates the execution/evidence baseline, not application modules, firmware, runtime schemas, API contracts, or an operational dashboard. Use reviewable Markdown tables and linked artifacts consistent with the existing planning documents; no new runtime dependency is required.
- **Record source identity and precedence.** Capture title, declared version where present, update date, repository revision or content identity, and reference for each governing source. The PRD owns scope and acceptance; AD-1–AD-15 own adopted technical decisions; the TRD derives contracts and gates; later adopted decisions take precedence over older UX assumptions; the guide and checklists own work order and evidence. An absent document version is recorded as absent, not invented. The reference implementation plan does not govern this project.
- **Create accountable ownership and dependency records.** Identify the Phase 00 execution/evidence lead, a named accountable owner for each of Phases 01–17, and a named owner for each gate T1–T7. Record supporting roles, dependency gates, expected outputs, and actual availability. One person may own multiple tracks. Missing assignments remain pending and prevent a claim that Phase 00 ownership is complete; do not invent people or infer commitments from a role title.
- **Preserve the execution sequence.** Phase 00 precedes hardware readiness. Complete Phase 01 before starting Phase 02 under the hardware-first schedule, even though their dependency graph otherwise permits parallel work. Later work follows its listed dependencies. Physical assembly/readiness keeps motor power disconnected and outputs disabled; actual movement remains gated until Phase 12.
- **Separate assessment facts from scheduling assumptions.** Record confirmed assessment instructions with their source and confirmation date, including timezone for any date/time. Preserve the reported four-week window as of 2026-11-06 and conditional 2026-12-04 planning target; neither establishes an assessment appointment. Obtain confirmation through the team/supervisor workflow. If confirmation is unavailable, record the responsible person, next action, and scheduling dependency. Assign actual milestone dates and contingency after assessment details and capacity are known; do not fabricate dates to fill a table.
- **Reconcile inventory without qualifying hardware.** Record prescribed item, expected quantity, reported purchased/available quantity, inspected quantity, exact model/variant where known, condition, evidence reference, inspection date, owner, and outstanding questions. Include the laptop/GPU/Windows, webcam, PS4 controller, Bluetooth/Wi-Fi, proposed network/route, and all prescribed hardware. PRD v1.1 is the reported-purchase baseline; neither older “not purchased” wording nor the current purchase report replaces an inventory check. Model or rating uncertainty stays explicit. Record only the network information needed for planning; keep credentials outside tracked artifacts.
- **Keep compatibility and approval at their existing gates.** Carry power/regulator suitability, charger/cell specifications, BMS connections, motor-pair/driver current and thermal compatibility, logic/wiring/programming access, and reset-disabled outputs into T2. Carry equipment and route verification into T3. No inventory entry, diagram, or baseline review closes an electrical gate. No additional procurement, charging, wiring, energizing, or movement is authorized by this phase.
- **Create exactly 29 top-level acceptance-index entries.** Cover FR-1–FR-18, NFR-1–NFR-6, and SM-1, SM-C1, SM-2, SM-3, SM-4 once each. A requirement may link multiple trials without becoming duplicate top-level entries. Each entry records its stable ID, source acceptance criterion, named owner, implementation phase(s), verification phase(s), planned test, required configuration identifiers, result status, evidence links, failures, and remaining issues. Initialize every result Pending, with no fabricated measurements or evidence links. Use an explicit pending reason for unavailable information.
- **Preserve the approved metrics verbatim in meaning.** SM-1 uses five objects with ten clearly visible presentations each, with at least 7/10 per object alerting within three seconds. SM-C1 uses ten separate ten-second scenes without a visually similar target, with at most one alerted scene. SM-2 requires physical wheel stopping within 0.5 seconds including loss detection. SM-3 requires twenty minutes without recharge, restart, or crash while exercising the complete system. SM-4 requires camera-event-to-laptop-display delay within 0.5 seconds with control and AI active. Record the detailed PRD trial conditions rather than replacing them with component-only proxies.
- **Separate result status from evidence level.** The index distinguishes planned, simulated, bench, integrated, and assessed evidence as applicable. A reference to a plan is not a test pass. Later trial records must capture what changed, release/configuration identifiers, conditions, checks, results including failures, evidence location, and remaining issues. Trace implementation and final verification to the guide's coverage tables; FR-18 also has controlled-integration and handoff evidence.
- **Maintain one blocker/decision register.** Each entry has a stable identifier, related requirement/gate, question or blocker, named owner, affected phase/work, evidence needed, next action, due condition or confirmed date, status, and resolution reference when available. Keep adopted decisions distinct from open qualification/configuration questions. All T1–T7 receive traceable entries or links. An open gate blocks its dependent work rather than granting permission through a default assumption.
- **Build on existing source control.** The repository already has Git history and a GitHub origin. Document and agree the team's review/issue workflow instead of creating another repository or imposing an unapproved branch/commit policy. Define appropriate ignore rules for secrets, runtime databases/records, and private images while retaining approved planning and sanitized assessment evidence. Inspect tracked content before claiming protection; an ignore rule alone does not remove already tracked data. Do not rewrite history or delete existing files as routine baseline setup.
- **Start the report and evidence handoff.** Establish a report outline covering approved scope, architecture, equipment and safety decisions, implementation, test methods/results, limitations, and demonstration, adjusted to confirmed assessment instructions. Document evidence locations and naming conventions, including a place for each later phase and final qualification. Creating an empty evidence index does not create trial evidence.
- **Keep implementation status honest.** Do not mark Phase 00 Done until its package and named ownership pass review. Assessment dates and technical questions may remain explicitly pending at their approved gates with owners and next actions. This does not waive dependent entry gates. Do not mark Phases 01–17 complete because their plans or source documents exist.

## Testing Decisions

- **Confirmed test boundary:** the user confirmed one acceptance boundary: review the completed baseline package as a whole for completeness, traceability, and honest status reporting. This is a document acceptance review, not a new application test harness.
- **What makes a good check:** assess whether an implementer, gate owner, verifier, or report author can answer a real handoff question using the package. Verify references against owning sources. Avoid checks tied to table layout, heading wording, internal helper functions, or a particular storage format.
- **Units under review:** the source baseline, ownership/dependency record, inventory, assessment/schedule record, acceptance/evidence index, blocker/decision register, source-control conventions, and report outline. These artifacts form one package; no runtime module is introduced or tested in Phase 00.
- **Prior art:** use the existing Phase 00 acceptance/evidence checklist, the implementation guide's phase/coverage tables and Definition of Done, PRD acceptance protocols, and TRD gate table. Repository inspection found planning artifacts and no application test suite to extend. Prior planning-review reports are examples of document review, not product qualification evidence.
- **Source check:** verify source references resolve, document identities match the baseline, adopted decisions remain adopted, and the PRD/architecture/TRD authority order is preserved. Any source change before handoff requires reconciliation of affected entries.
- **Ownership/dependency check:** account for all 18 phases and seven gates, verify named accountable owners and known availability, and confirm the Phase 01-before-02 execution order and Phase 12 movement gate remain visible. An unassigned phase or gate fails the ownership check.
- **Inventory check:** reconcile every prescribed component and equipment category with reported and inspected status. Missing variants or ratings must yield explicit open items; they must never imply compatibility, approval, or observed availability.
- **Assessment check:** confirm that every date, time, format, and capacity statement either has confirmation evidence or is visibly pending with an owner and next action. The conditional planning target must not appear as a confirmed assessment deadline.
- **Coverage check:** compare the index ID set with all 29 required IDs; reject omissions, duplicates, unsupported passes, and weakened metrics. Verify planned tests and phase mappings against the owning sources, including both control modes, recovery, offline operation, retention, fixed-desk multi-room operation, and advisory proximity warning.
- **Evidence check:** verify all initial results are Pending, placeholders are identified, result and evidence level are separate, and configuration/failure fields exist. A simulated, bench, or planning artifact must not establish assessed whole-system success.
- **Gate check:** verify T1–T7 each have accountable ownership, required exit evidence, affected work, and next action. Ensure the package does not invent electrical values, timeouts, model settings, approvals, purchases, or qualification results.
- **Source-control check:** inspect the proposed tracked change set and relevant ignore behavior for secrets, runtime records, and private images. Report existing exposure if found without printing secret content or automatically rewriting history. No push or new review policy is required to demonstrate this check.
- **Exit review:** record reviewer, review date, baseline identity, checks performed, findings, disposition, and remaining gated items. Phase 00 is acceptable when its baseline artifacts are coherent and complete, owners are named, every requirement has a planned verification route, and unresolved facts are explicitly assigned. Technical gates may remain open; their dependent work remains blocked.

## Out of Scope

- Performing Phase 00 merely by writing this specification, assigning real people without confirmation, or contacting the supervisor automatically.
- Purchasing, installing paid tools, assembling, wiring, charging, energizing, or moving hardware; electrical design and T2 clearance belong to Phase 01 and subsequent reconfirmation gates.
- Choosing exact dependency versions, model checkpoints, watchdog values, electrical ratings, recognition thresholds, proximity distances, branding, or device mappings that remain gated.
- Building the frontend, backend, database, managed-media lifecycle, AI worker, firmware, input adapters, camera pipeline, launcher, or runtime safety coordinator.
- Running product qualification, declaring performance passes, or closing T1–T7 without their owning evidence.
- Revising approved requirements or architecture, weakening the multi-room demonstration, dropping a control mode, or reducing the required safety/history/retention/offline behavior.
- Creating additional repositories, imposing a new commit policy, rewriting history, publishing runtime/private data, or adding a cloud service.
